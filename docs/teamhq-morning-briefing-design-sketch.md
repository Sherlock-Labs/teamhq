# TeamHQ Morning Briefing — Design Sketch

**Robert (Designer) · March 2026**

---

## The Core Problem

The CEO wakes up. TeamHQ has been running agents for 8 hours. The current dashboard shows a general-purpose pipeline overview — useful, but it doesn't answer the one question that matters at 8am: *do I need to do anything right now, or can I get coffee?*

The morning briefing is a different thing. It's not a dashboard. It's a **briefing document that happens to be interactive.** Think a daily memo from your chief of staff, not a Jira board.

---

## Design Principles for This View

1. **Verdict first, detail second.** The CEO's first impression — before reading a single line — should be the overall system health. Green = all clear. Amber/red = act now.
2. **Actions surface before information.** Things the CEO must do come before things they should know.
3. **Inline actions, not page jumps.** Approving a review or responding to an agent question should happen in-place, without navigating away.
4. **Information has a half-life.** Completed work from last night becomes less urgent as the day goes on. Blocked items stay urgent until resolved. The layout should reflect this.

---

## Page Structure

The briefing lives at `index.html` (the Dashboard route). It replaces — or augments — the current metric-card layout. The sidebar, header bar, and footer remain unchanged.

The main content area is a **single vertical column**, not a grid. The column is narrower than the full content width (max ~720px centered, or left-aligned with a right-side gutter for context). This creates a document-like reading experience rather than a dashboard scan.

---

## Section 1: Status Banner

**Position:** Pinned at the top of the main content area, full width, above everything else.

**Purpose:** The 3-second verdict. Can be read at a glance before the CEO's eyes focus.

**Visual:** A single horizontal bar, slightly taller than the current header chips (~48px). Background color signals state:

- **Green-tinted** (`#F0FDF4` background, `#006B3F` left border): System nominal — no immediate action needed
- **Amber-tinted** (`#FFFBEB` background, `#D97706` left border): Items need attention
- **Red-tinted** (`#FEF2F2` background, `#DC2626` left border): Something is blocked or failing

**Content (left to right):**
```
● NOMINAL — 3 reviews waiting · 2 projects advancing · last heartbeat 47m ago
                                                                    [Run Heartbeat]
```

The dot pulses if a heartbeat is running. The summary phrase is machine-generated by the latest Thomas assessment. The "Run Heartbeat" button appears only when the last heartbeat is >2hrs ago or when there are unresolved blocked items.

**Empty state:** If no heartbeat has run yet, the banner reads: "No briefing yet — run a heartbeat to get Thomas's assessment."

---

## Section 2: Needs Attention

**Position:** Immediately below the status banner.

**Purpose:** Every item here is an action. The CEO cannot ignore this section. Zero items = section is hidden entirely (no empty state message needed — absence is clear).

**Visual:** Section header: `NEEDS YOUR ATTENTION` in the `subtle-label` style, followed by stacked cards. Each card has a **3px left border** in the urgency color (red for blocked/failed, amber for awaiting-review), white background, `premium-shadow`.

Three item types appear here, each with its own card pattern:

### 2a. Review Queue

One card per pending review. Inline approve/reject without page navigation.

```
┌────────────────────────────────────────────────────────┐
│ ● REVIEW  │  PIPELINE-REVIEW-GATES  │  Robert › Alice  │
│                                                        │
│  Design review for pipeline review gates feature.      │
│  Robert submitted 3h ago.                              │
│                                                        │
│  [View Diff]  ──────────────  [Reject]  [Approve →]    │
└────────────────────────────────────────────────────────┘
```

The card is collapsed by default. Clicking "View Diff" expands an inline preview (the design spec delta or code diff, rendered as a collapsible panel below the action buttons). "Approve →" advances the pipeline. "Reject" opens a one-line reason field.

### 2b. Blocked Items

One card per blocked work item. Inline redirect input.

```
┌────────────────────────────────────────────────────────┐
│ ● BLOCKED  │  ROADMAP-TOOL  │  Thomas                  │
│                                                        │
│  Backend API for themes endpoint returning 500.        │
│  Blocked for 6h. Jonah flagged missing migration.     │
│                                                        │
│  [See Context]  ──  Redirect: ________________  [Send] │
└────────────────────────────────────────────────────────┘
```

The redirect input is a single text field pre-focused if the CEO clicks the card. Sending a redirect posts it to the CEO Inbox and triggers Thomas's next heartbeat.

### 2c. Agent Questions

Direct asks from agents that require CEO input before work can proceed.

```
┌────────────────────────────────────────────────────────┐
│ ● QUESTION  │  FROM: THOMAS  │  4h ago                 │
│                                                        │
│  "Should I scope the mobile version for v1, or defer   │
│   it to post-launch? Affects 2 work items."            │
│                                                        │
│  Reply: _______________________________  [Send]        │
└────────────────────────────────────────────────────────┘
```

Reply field is a short text input. Sending adds it to the CEO Inbox and optionally triggers a heartbeat.

## Section 3: Overnight Activity

**Position:** Below the "Needs Attention" section (or where that section would be if empty).

**Purpose:** Informational. What happened while you were away. The CEO reads this for context, not to act.

**Visual:** Lighter treatment than Section 2. No colored left-borders. Section header: `WHILE YOU WERE AWAY` in `subtle-label` style.

Three sub-components:

### 3a. Thomas's Assessment (if a heartbeat ran overnight)

One collapsed card showing the summary paragraph from the latest heartbeat. Expands inline to show the full assessment + decisions list.

```
┌────────────────────────────────────────────────────────┐
│  Thomas's Assessment  ·  Mar 18 · 2:14am  ·  [Expand] │
│                                                        │
│  "Two projects advanced. Alice completed frontend      │
│   implementation for review-gates. Jonah unblocked     │
│   the schema migration. One item needs CEO input…"    │
└────────────────────────────────────────────────────────┘
```

If no overnight heartbeat ran, this card reads: "No heartbeat ran overnight. Thomas last ran 14h ago." with a "Run Now" link.

### 3b. Completed Work

A compact list (not cards) of work items completed since the CEO's last session. Agent avatar + item title + timestamp. Tappable to see the full work item detail (slides in from right, same pattern as the heartbeat detail panel).

```
  ✓  Alice   Frontend implementation — pipeline review gates   2h ago
  ✓  Jonah   Schema migration for review states               3h ago
  ✓  Robert  Design spec — review gates                       5h ago
```

Truncated at 5 items. "View all 12 completed" link to a filtered tasks view.

### 3c. Autonomous Decisions

A count + expandable list of decisions Thomas made without CEO input. This is a transparency log, not an action queue.

```
  Thomas made 4 autonomous decisions overnight  [Show]
```

Expanded: the same decision-card pattern from autonomy.html, but rendered inline here. Agent-spawned, work-item-created, pipeline-advanced type decisions listed compactly.

---

## Section 4: What's Next

**Position:** Below the activity section.

**Purpose:** Pipeline status and upcoming work. The CEO uses this for situational awareness — where are we headed today?

**Visual:** Two-column layout within the section (contrasting with the single-column doc feel above). Section header: `PIPELINE STATUS`.

### 4a. Active Pipelines (left, ~60% width)

One row per active project. Compact horizontal pipeline progress indicator.

```
  ROADMAP-TOOL     [Scope ▓▓▓▓▓░░░░░ Frontend]   Thomas → Alice
  REVIEW-GATES     [QA ▓▓▓▓▓▓▓▓▓░░ Review]        Enzo
```

Each row: project name (uppercase, truncated), a mini progress bar showing pipeline phase, current agent. Click to go to `projects.html` with that project selected.

Blocked projects show in amber with a blocked indicator instead of the progress bar.

### 4b. CEO Inbox (right, ~40% width)

The standing directive input, always present. Smaller visual weight here than on `autonomy.html` — this is a secondary action, not the primary focus.

```
  ┌─────────────────────────────────────┐
  │ Give Thomas direction for today...  │
  │                                     │  [Add]
  └─────────────────────────────────────┘

  ● Start scoping QuoteVoice billing flow
  ● Hold all new projects until v1.2 ships
```

Pending directives shown below the input with remove buttons. Identical behavior to `autonomy.html` but visually smaller (11px text, less padding).

## Notification Model

Two tiers, never more:

**Tier 1 — Action Required** (surfaced in Section 2):
- Pending reviews
- Blocked work items
- Agent questions

These appear in Section 2 with colored left-borders. They do not appear anywhere else on the page. Count is also reflected in the Status Banner summary line.

**Tier 2 — Informational** (Section 3, Section 4):
- Completed work
- Autonomous decisions
- Pipeline progress

These are read-only. No badges, no red colors. The CEO reads them to stay oriented, not to act.

**No persistent notification badges on the sidebar.** The morning briefing itself is the notification surface. The Reviews sidebar badge (currently implemented) can remain for non-briefing contexts, but the briefing absorbs that role on the dashboard route.

---

## Progressive Disclosure Pattern

Three depth levels, consistent across the page:

**Level 1 — Scan (default view):** Every item visible as a card or row with summary text. No detail visible. CEO can assess the full situation without any clicks.

**Level 2 — Inspect (one click/expand):** A card expands inline to show supporting context. For reviews: the diff preview. For heartbeats: the full assessment. For decisions: the reasoning list. Expansion is in-place — no navigation, no modal.

**Level 3 — Deep dive (link out):** If the CEO wants full context — the complete project history, full work items, raw agent output — a link takes them to the relevant page (`projects.html`, `autonomy.html`, `reviews.html`). This is escape hatch, not primary flow.

**Rule:** The CEO should be able to approve every pending review and respond to every agent question without leaving the briefing view.

---

## Relationship to Existing Pages

The morning briefing **replaces the current index.html dashboard** as the default landing view. The existing metric-card grid (Pipeline Phase, Shipped, In Progress, Team Size) is demoted — it can move to a collapsible "System Stats" section at the bottom of the page, or to a secondary "Overview" tab. It's useful context but not urgent.

The `autonomy.html` page remains the destination for:
- Full heartbeat history and log
- Autonomy configuration (interval, enable/disable)
- The primary CEO Inbox interface

The briefing is a **curated summary** that surfaces what matters right now. The detail pages are where you go to dig in.

## Open Questions (for Thomas / CEO)

1. **Heartbeat timing:** Should the briefing show a "since your last login" window, or always show the last 8 hours? Time-based feels more natural for a "morning briefing" metaphor, but login-based is more accurate.

2. **Review approval flow:** Is a single-click approve sufficient, or should there be a lightweight confirmation step? Given that approvals advance the pipeline (potentially spawning new agents), a brief confirmation may be warranted.

3. **Agent questions persistence:** Where do agent questions live in the data model? Currently the CEO Inbox is a directive queue for Thomas. Agent questions might be a different channel — or are all agent questions routed through Thomas?
